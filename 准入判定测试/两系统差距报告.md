## 二、逐维度差距明细

### D4 机查覆盖（5 vs 3 — 大差距）

B 有 14 个 `check_*.py` 且与 orchestrator §4 机查表完全对齐；C 只有 5 个，**缺失 9 个**：

| 缺失机查 | B 侧功能 | 对 C 的影响 |
|---------|---------|-----------|
| `check_code_hygiene.py` | 交付代码内部流程词黑名单 + emoji 禁查 | C 交付代码可能泄露内部流程词 |
| `check_workspace_hygiene.py` | 项目根设计外垃圾/编译副产物扫描 | C 工作区卫生无人把关 |
| `check_latex_env.py` | xelatex/宏包/中文字体预检 + 编译降级机制 | C 缺编译预检与降级路径 |
| `check_abstract_guard.py` | 摘要边界机判 + 篇幅量化 + 关键词加粗 | C 摘要有无超页无机器兜底 |
| `check_tex_numbers.py` | 正文数值 vs solution.json 一致性 | C 无跨产物数值校验 |
| `check_modeling_artifacts.py` | 图表双格式配对/绝对路径 | C 图表契约校验缺位 |
| `check_viz_tests.py` | 绘图 4 回归测试执行器 | C 有 test_* 但无执行机查兜底 |
| `check_convention_refs.py` | 惯例编号引用完整性对账 | C 惯例引用悬空无检测 |
| `check_card_refs.py` | 卡片→模板引用完整性 | C 卡片引用悬空无检测 |

C 侧最厚的 `check_solution_json_c.py`（九字段契约+泄漏声明+量纲四元组）是数据题专属强项，值得承认。

### D6 编排协议（5 vs 3 — 大差距）

### D2 求解器封装（4 vs 2 — 定位性差异）

C 无 mip/nlp/metaheuristic/cp/solver_backend/graph_utils 六件套——**属合理缺位**（数据题不需要优化主干），C 的 data_modeling_template.py（PARAMETERS+TASK_HOOKS+泄漏防线+时序保序划分）质量良好。但注意：C 的卡片 12（数据+优化衔接）承诺的优化衔接能力**无求解器脚手架支撑**（准入判定实验缺陷 D3 已证）。

## 三、C 系统独有资产（值得考虑反向回流 B 的）

1. `visualization_style.py` 的 `plot_heatmap/tornado/line/bar/scatter` 便捷封装——B 若遇数据子问（如借卡协议 C4③启用时）现成可用
2. `stage5_review.json 禁读`机制——防止评审被自审分数锚定
3. `data_modeling_template.py` 泄漏三防线（预处理仅训练集拟合/时序保序划分/基线对比）
4. requirements.txt 含 scikit-learn/statsmodels——B 的 requirements 缺这两个（借卡处理统计子问时需自行补装）

## 四、B 系统自身缺口（审计旁证）

1. requirements.txt 缺 `ortools`/`networkx`（cp_solver/graph_utils 换机复现会缺依赖）
2. paper-writer（~11139）/independent-reviewer（~10100）超 9500 建议值，逼近 12000 硬上限
3. 打包/代码卫生黑名单为手工字符串列表，两份代码存在漂移风险

## 五、归因分析

- **差距根源 = 实战打磨差**：B 积累了 2026-08-B1/B2/C1/C2/C3/C4 六个规则批次 + 10 板块质量排查（约 40 问题修复闭环）；C 自 v2.0 起仅补过一次 DOE 卡片（13_实验设计），从未做过治理排查。
- **差距性质二分**：定位性差异（D2 优化求解器）不应补齐；继承性差异（D4/D6/D9/D10/skills/写作规范——全部与题型无关）是纯欠账，移植零冲突。
- **治理缺口自锁**：C 无 git 仓库（无根 .gitignore、无治理目录），意味着 C 的共享文件修改没有 commit 绑定机制——防过拟合铁律 6 在 C 侧无法执行，这是欠账能否偿还的前提问题。
